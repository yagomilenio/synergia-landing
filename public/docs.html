Cómo funciona Synergia por dentro

Esta página documenta el comportamiento real de los dos repositorios — synergia-server y synergia-client— a nivel de código: rutas HTTP exactas, mensajes del protocolo WebSocket, esquema de config.toml, fórmulas de pago y el modelo de datos completo. Cada afirmación de esta página está contrastada directamente contra el código fuente en el momento de escribirla; si algo cambia en el repositorio, esta página puede quedar desactualizada respecto a él, nunca al revés.

00 Introducción

Synergia es una plataforma de computación distribuida voluntaria con incentivos económicos. Cualquiera puede publicar una tarea apuntando a un repositorio de GitHub que contenga un config.toml y un Makefile; la red de workers se encarga de repartírsela, ejecutarla de forma aislada y devolver resultados verificados. A cambio, cada worker recibe créditos internos proporcionales al coste computacional real (ciclos de CPU, RAM y, si aplica, vatios de GPU) que aportó.

El sistema distingue tres roles, que puede ejercer la misma cuenta en distintos momentos:

  • Publisher — publica la tarea (POST /task), paga el coste fijo de publicación y financia los pagos a quienes la procesen.
  • Worker — se suscribe a una tarea, consume chunks por WebSocket, ejecuta el Makefile del repositorio dentro de un contenedor aislado y sube los resultados.
  • Servidor — reparte el trabajo en RabbitMQ, verifica resultados por consenso, liquida pagos y calcula reputación.
Repositorios: el backend vive en synergia-server (API REST, API WebSocket, infraestructura Docker); el cliente CLI y el worker viven en synergia-client. Son proyectos independientes con su propio versionado.

Por qué dos APIs separadas

La API REST resuelve operaciones puntuales (crear cuenta, publicar tarea, consultar progreso, subir un resultado). La asignación de chunks, en cambio, necesita una conexión persistente de baja latencia con backpressure: por eso vive en un servicio FastAPI distinto, montado sobre WebSocket, que habla directamente con RabbitMQ vía aio-pika usando prefetch_count para controlar cuántos mensajes puede tener "en vuelo" cada worker.

Aislamiento de ejecución

Cada chunk se ejecuta dentro de un contenedor Docker propio del worker (no del servidor). El contenedor no tiene privilegios de root para el código de la tarea, tiene una tabla de iptables que bloquea toda salida de red salvo la explícitamente permitida, y sus binarios curl/wget están sustituidos por wrappers en C que registran cada descarga externa. Todo esto se detalla en Seguridad.

02 Flujo completo de una tarea

1. Publicación (POST /task)

El cliente, antes de llamar a la API, calcula localmente el hash SHA-256 del repositorio (tras aplicar [hash].exclude) y el commit actual, y los envía junto al resto de campos. En el servidor:

  1. Se descarga y parsea el config.toml del repositorio (load_config()), obteniendo si la tarea es deterministic, si sus inputs son dynamic y el número total de items (cfg().inputs.total()).
  2. Se verifica que el publisher tiene saldo suficiente para TASK_COST (créditos fijos de publicación, configurables en config.json).
  3. Se inserta la tarea en Oracle y se registra la transferencia de TASK_COST hacia la cuenta de sistema SYSTEM_FEES.
  4. Se generan los chunks (Producer.publish_chunks) y se publican en la cola RabbitMQ task_{id}.

Chunking con presupuesto de memoria

El tamaño de cada chunk no es fijo: generate_chunks() calcula el tamaño de chunk más grande posible tal que la cola completa (todos los mensajes {"index", "count"} más el overhead de AMQP) no supere 512 KB en memoria, para tareas con millones de items. El cálculo evita construir la lista completa en memoria: suma analíticamente los dígitos de cada índice en cada tramo de longitud (1 dígito, 2 dígitos, …) en vez de iterar item a item.

2. Suscripción y consumo (WebSocket)

El worker abre ws://host:8001/ws/task/{task_id}?token={jwt}&n_consumes={n} y envía {"action": "next", "n": N} para pedir hasta N chunks. El servidor ajusta el prefetch_count de su canal AMQP a ese valor y hace ack/nack de los mensajes anteriores según si su proceso terminó en SUCCESS en base de datos — así un worker que se cae a media ejecución devuelve el chunk a la cola automáticamente.

3. Ejecución local (worker)

Antes de la primera ejecución, el worker levanta el contenedor, aplica make setup (con red permitida solo hacia [network].allowed_hosts y DNS), calcula el hash del repo antes y después del setup, descarga los ficheros de [download] si los hay, y aplica la política final de iptables (DROP por defecto). Por cada chunk:

  1. make clean para no arrastrar salidas previas.
  2. make run con variables de entorno según el tipo de input: START=/END= para rangos, WORD= para un único item dinámico, WORDS= (separado por espacios) para file_single.
  3. Medición con perf stat (ciclos de CPU) y, si hay GPU, con nvidia-smi (potencia y memoria de vídeo).
  4. Empaquetado determinista del resultado (tar --sort=name --mtime=... --owner=0) y subida vía upload_results.py.

4. Verificación y pago

En tareas deterministas, cada subida recalcula cuál es el resultado canónico del proceso: el result_file_id con más ejecuciones SUCCESS coincidentes gana (empate roto por la ejecución más antigua). Solo el nodo canónico cobra directamente del publisher; el resto de nodos cuyo hash coincide con el canónico cobran una parte proporcional pagada por la cuenta de sistema SYSTEM_FEES al confirmar. En tareas no deterministas no hay disputa posible: el primer resultado subido cobra directamente. Detalle completo en Modelo económico.

5. Cierre de la tarea

Las tareas no dinámicas se marcan COMPLETED automáticamente cuando items_procesados >= total_items, momento en el que el servidor borra la cola de RabbitMQ asociada. Las tareas dinámicas se cierran manualmente con PATCH /task/{id}/status. Si el saldo del publisher cae a cero o por debajo del coste estimado del siguiente chunk (media + desviación típica de coste por item, calculadas de forma incremental), todas sus tareas se pausan automáticamente.

[inputs] — los 6 tipos reales de entrada

type es el discriminador y activa exactamente una subsección:

directory

[inputs]
type = "directory"

[inputs.directory]
path       = "inputs/images"
recursive  = false
extensions = [".jpg", ".png"]
sort_order = "filename"

Enumera ficheros de un directorio del repo GitHub (GithubUtil.list_dir) y les asigna índices 0..N-1.

file_multi

[inputs]
type = "file_multi"

[inputs.file_multi]
glob   = "inputs/**/*.png"
format = "binary"   # binary | text | image | video

Selecciona ficheros por patrón glob remoto sobre el repositorio (GithubUtil.list_glob).

file_single

[inputs]
type = "file_single"

[inputs.file_single]
path        = "inputs/lista.txt"
format      = "text"     # text | json | image | video | binary
delimiter   = "\n"
encoding    = "utf-8"
skip_header = false
# opcional, para ficheros binarios indexados:
index_file  = "inputs/indice.bin"
index_len   = 16

Un único fichero remoto que se trocea. En modo text/sin índice, el worker usa awk con el delimiter como RS para extraer solo las líneas del rango asignado sin descargar el fichero completo. Si se define index_file + index_len, el worker lee ese índice binario con dd para calcular el offset y tamaño exactos del bloque a extraer del fichero real — pensado para datasets binarios grandes (p. ej. diccionarios de contraseñas) donde no es viable partir por líneas de texto.

range_continuous

[inputs]
type = "range_continuous"

[inputs.range_continuous]
start = 0
end   = 999999
step  = 1

Rango numérico continuo. Internamente se representa como un range() de Python para no colapsar memoria con rangos de millones de valores.

range_discrete

[inputs]
type = "range_discrete"

[inputs.range_discrete]
values = [1, 5, 23, 47, 200, 9999]

Lista explícita de valores no contiguos — útil para reprocesar solo items concretos que fallaron.

dynamic

Sin subsección propia. Marca la tarea como dinámica: no tiene un total de items fijo de antemano — se añaden en caliente vía POST /task/{id}/input — y el worker recibe cada item como value individual (usado, por ejemplo, para colas de prompts a un LLM).

Nota sobre la sección [runner]: versiones anteriores de esta documentación describían una sección [runner] con campos command, arg_start, arg_end, etc. Esa sección no existe en el parser real (configuration_interpreter.py no define ninguna clase RunnerConfig ni lee raw["runner"]). Cómo se ejecuta cada chunk lo define el Makefile del propio repositorio de la tarea — ver siguiente sección.

04 Contrato del Makefile

Todo repositorio de tarea debe exponer tres targets. El worker los invoca dentro del contenedor con cd /repo && make <target>:

TargetCuándo se ejecutaVariables de entorno que recibe
setupUna sola vez, antes del primer chunk (con caché salvo --no-cache)Ninguna — es responsable de instalar dependencias propias de la tarea, dentro de la red restringida a [network].allowed_hosts
runPor cada chunk asignadoSTART / END (rangos) · WORD (item dinámico único) · WORDS (lista separada por espacios, file_single) · sin variables si la tarea no tiene [inputs]
cleanAntes de cada run y al finalizarNinguna — debe borrar cualquier salida previa para que [outputs] no acumule ficheros obsoletos
 
# Ejemplo real de invocación (worker/worker.py)
cmd = f"cd /repo && make run START={start} END={end}"
cmd = f"cd /repo && make run WORD={shlex.quote(value)}"                       # input dinámico
cmd = f"cd /repo && make run WORDS={shlex.quote(' '.join(words))}"            # file_single

Esta decisión de diseño es deliberada: no hay wrappers específicos por lenguaje (Python, C++, Rust…). Si el código corre con make run START=0 END=999 en local, corre en Synergia.

Configuración local

Ciclo por chunk (resumen de worker.py)

  1. Comprueba con el servidor si la tarea sigue activa (get_continue_information).
  2. Crea el proceso en el servidor (POST /task/{id}/process) — si ya existe, cuenta como error y tras 3 seguidos detiene el worker.
  3. make clean && make run … dentro del contenedor, con perf stat y (si hay GPU) nvidia-smi midiendo el consumo.
  4. Empaqueta el resultado de forma determinista y lo sube con upload_results.py, autenticado con el JWT del worker.
  5. Ajusta dinámicamente cuántos chunks pedir a continuación según cuánto tardó el bloque anterior, para intentar subir resultados cada ~60 segundos (UPLOAD_INTERVAL).

Si la tarea exige verificación (contador chunks_since_last_verification por encima del umbral process_until_confirmation del servidor), el worker recibe {"status": "verification_required"} por WebSocket y debe ejecutar confirm-process antes de que se le sirvan más chunks nuevos.

Subida de resultados: sharding por hash

Los ficheros no se guardan por execution_id: se calcula su SHA-256 en streaming (bloques de 1 MB) mientras se escriben a disco, y se guardan en storage/{2 primeros hex del hash}/{hash completo} — el mismo esquema de sharding de 256 subdirectorios que usa git. Si dos ejecuciones distintas producen exactamente el mismo fichero, se deduplica automáticamente y solo se guarda una copia física.

09 API WebSocket

ws://host:8001/ws/task/{task_id}?token={jwt}&n_consumes={n}

Conexión persistente, una por worker por tarea. El servidor valida el JWT antes de aceptar el handshake (código de cierre 1008 si es inválido) y hace de puente hacia una cola RabbitMQ dedicada, aplicando prefetch_count = n_consumes.

Mensajes que envía el worker

MensajeEfecto
{"action": "next", "n": 4}Pide hasta 4 chunks nuevos (ajusta el prefetch_count si n cambió respecto a la conexión).
{"action": "confirmation_done"}Indica que el worker ya resolvió la verificación pendiente pedida por el servidor.

Respuestas del servidor

MensajeSignificado
{"status": "empty"}La cola no tiene chunks disponibles en este momento; el worker debe reintentar.
{"status": "paused"}La tarea no está ACTIVE y el usuario no es su publisher.
{"status": "completed"}La tarea terminó; el servidor cierra la conexión.
{"status": "verification_required"}El worker superó el umbral de chunks sin verificar y debe llamar a confirm-process antes de seguir.

Reconciliación al desconectar

Si la conexión se cierra (caída del worker, Ctrl+C, red), el servidor comprueba en base de datos si cada chunk en vuelo terminó en SUCCESS: si es así hace ack definitivo en RabbitMQ; si no, hace nack(requeue=True) para que otro worker pueda tomarlo. También cancela ejecuciones incompletas y limpia procesos huérfanos de ese usuario sin ninguna ejecución completada.

10 Seguridad y autenticación

Cuentas

  • Contraseñas con Argon2 (argon2-cffi), nunca en texto plano ni con hashes reversibles.
  • Verificación de email obligatoria antes de poder hacer login local (token JWT de un solo propósito, 24h).
  • Registro local restringido por dominio de correo (lista configurable en el servidor).
  • OAuth 2.0 con Google y GitHub, con estado anti-CSRF de un solo uso en caché con expiración (5 min).
  • Los usuarios nuevos por OAuth reciben los mismos créditos iniciales que el registro local.

Sesión

JWT firmado con HS256, expiración de 24 horas, enviado en el header token (no es un Bearer estándar). El sub del payload es el account_id.

Aislamiento del contenedor worker

El Dockerfile del worker aplica varias capas de reducción de privilegios sobre python:3.12-slim:

  • El código de la tarea corre como usuario worker, sin privilegios de root.
  • Los binarios reales curl/wget se renombran a curl.real/wget.real; en su lugar se instalan wrappers en C, propiedad de un usuario dedicado net_user con bit setuid, que registran cada descarga en un log de solo lectura para el proceso de la tarea (external_deps.log).
  • iptables permite tráfico establecido, loopback, DNS (puerto 53) y las UID de root/net_user/uid 42; todo lo demás se descarta con una regla DROP final — incluidos los hosts declarados en [network].allowed_hosts, que se insertan como reglas ACCEPT explícitas antes de aplicar el resto de la política.
# worker/container/iptables.sh (real)
iptables -I INPUT -m state --state ESTABLISHED,RELATED -j ACCEPT
iptables -I INPUT -i lo -j ACCEPT
iptables -I OUTPUT -o lo -j ACCEPT
iptables -I OUTPUT -m owner --uid-owner root -j ACCEPT
iptables -I OUTPUT -m owner --uid-owner 42 -j ACCEPT
iptables -I OUTPUT -m owner --uid-owner net_user -j ACCEPT
iptables -I OUTPUT -p udp --dport 53 -j ACCEPT
iptables -I OUTPUT -p tcp --dport 53 -j ACCEPT
iptables -A OUTPUT -j DROP

Integridad del repositorio

El worker calcula el hash SHA-256 del contenido de /repo antes y después de make setup (excluyendo las rutas de [hash].exclude, típicamente artefactos generados), y combina ambos en un hash final que se compara contra el que el servidor registró al publicar la tarea (repo_snapshot_hash). Si no coincide, POST /task/{id}/process rechaza el chunk con 409 — evita que un worker ejecute una versión manipulada del código de la tarea.

11 Modelo económico — fórmulas reales

No es una blockchain de propósito general. Synergia usa una base de datos centralizada con una tabla de transferencias inmutable (ver más abajo), no un libro contable distribuido: evita la complejidad de wallets, gas y consenso entre nodos sin renunciar a la trazabilidad total de cada movimiento de créditos.

Coste de una ejecución

Al subir un resultado, el servidor calcula el coste real con estas constantes (api.py::create_result):

CPU_COST_PER_CYCLE    = 1e-9
RAM_COST_PER_GB_SEC   = 0.001 * (887 / 1.985)
GPU_COST_PER_WATT_SEC = 0.0001 * (887 / 4.3)

ram_gb  = ram_avg / (1024 ** 3)   # bytes -> GB
vram_gb = vram_avg / 1024         # MB -> GB

amount = (
    cpu_cycles * CPU_COST_PER_CYCLE +
    ram_gb  * duracion * RAM_COST_PER_GB_SEC +
    vram_gb * tdp_w * duracion * GPU_COST_PER_WATT_SEC
)

cpu_cycles viene de perf stat, ram_avg/vram_avg/tdp_w del worker (nvidia-smi si hay GPU), y duracion es el tiempo real transcurrido entre la creación y la finalización de la ejecución en base de datos.

Pago no determinista

Sin ambigüedad posible: el publisher paga directamente al worker que subió el resultado.

Pago determinista (verificación cruzada)

  1. Se recalcula el resultado canónico del proceso: el result_file_id con más ejecuciones SUCCESS coincidentes gana (empate por la ejecución más antigua). No hace falta que sean exactamente dos nodos — es mayoría entre todas las ejecuciones de ese chunk.
  2. Si el canónico cambia respecto a antes de esta subida: se revierte el pago anterior (transferencia de vuelta al publisher), se paga al nuevo canónico y se reparte una recompensa entre quienes confirmaron el cambio, pagada por la cuenta de sistema SYSTEM_FEES — no por el publisher.
  3. Si el canónico no cambia y este worker coincide con él (pero no es quien ya cobró), recibe una fracción de la recompensa de confirmación, también desde SYSTEM_FEES.
  4. Tras cada pago se recalcula la reputación de los workers afectados.

Reputación

Se recalcula por cuenta como un porcentaje: de todo el dinero que un worker ha cobrado como no-canónico (es decir, sus ejecuciones donde otro nodo distinto resultó ser el canónico), qué proporción coincide en hash con el resultado canónico real. Penaliza a quien sistemáticamente diverge del consenso y premia la consistencia.

Auto-pausa por saldo

El servidor mantiene, de forma incremental, la media y la desviación típica del coste por item de cada tarea (avg_cost_per_item, sum_sq_cost). Si el saldo del publisher es igual o inferior a cero, o inferior al coste estimado del siguiente chunk (media + desviación), todas sus tareas activas se pausan automáticamente hasta que recargue saldo o cancele.

Priorización de qué verificar

Cuando un worker debe confirmar un resultado, el servidor no elige al azar: ordena los procesos pendientes combinando baja reputación del canónico actual (inversa de reputation + 1) con la desviación del coste pagado respecto a la media y desviación típica de la tarea — prioriza verificar primero lo que más "huele" a resultado anómalo o de un nodo poco fiable.

12 Modelo de datos (Oracle)

Trece tablas relacionales. Las claves foráneas circulares process ⇄ execution modelan que un proceso apunta a su ejecución canónica y cada ejecución pertenece a un proceso.

La tabla transfer: un libro contable inmutable

Es una Oracle Blockchain Table, no una tabla relacional normal. Cada fila (transferencia de créditos entre dos cuentas) queda encadenada criptográficamente con SHA2-512 a la anterior: 

CREATE BLOCKCHAIN TABLE transfer (
    id NUMBER(19) NOT NULL,
    from_account_id NUMBER(19) NOT NULL,
    to_account_id   NUMBER(19) NOT NULL,
    task_id NUMBER(19), process_id NUMBER(19),
    amount NUMBER(20,4) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL
)
NO DROP UNTIL 31 DAYS IDLE
NO DELETE LOCKED
HASHING USING "SHA2_512" VERSION "v1";

NO DELETE LOCKED significa que ninguna fila puede borrarse nunca, ni siquiera por un administrador; NO DROP UNTIL 31 DAYS IDLE impide eliminar la tabla completa si ha habido actividad reciente. El código refleja esta restricción explícitamente: las consultas de pago que leen transfer nunca usan FOR UPDATE porque la propia base de datos rechaza bloquear filas de una tabla inmutable — es la propia plataforma, no una convención de aplicación, la que impide reescribir el historial de créditos.
